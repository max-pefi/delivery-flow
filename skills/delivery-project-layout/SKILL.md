# delivery-project-layout — 项目布局助手（只读）

## 它是什么

项目跑了一段时间，根目录和阶段目录里往往堆了一堆文件——基线PRD、临时草稿、未来规划、客户待填、招标审计……分不清谁是谁。本 skill 把"整理"这件事**分成两步**：

1. **扫描出方案**（本 skill 做）— 调 `delivery layout --root . --json`，把建议念给人
2. **执行**（**人不点头，AI 不动**）— 方案可以是"建子目录 + 移文件"，但**当前版本不动文件**，由人手动 `mv` 或未来 `--apply` 执行

## 它不做什么（红线）

1. **不移动任何文件**——`delivery layout` 是只读命令
2. **不创建任何文件**——产物 `.draft.` 由各阶段 skill 自己管
3. **不动机器文件**（`SPEC.md` / `project-progress.yaml` / `_映射表.json` 等）
4. **不动关卡产物**（`客户确认记录-*` / `验收报告` / `评测报告`）
5. **不替人拍板**——多模块 vs 单模块、主题类目怎么分，都先问

## 何时触发

- 用户说"项目文件乱了 / 整理项目 / 按主题分类 / 按模块分类"
- 用户在 `delivery check` 后问"04-需求分析 目录怎么这么多文件？"
- 用户说"我新加了一个模块，要建子目录"

## 工作流

```
用户：「项目文件乱了，整理一下」
  ↓
AI：明白。我会调 `delivery layout --root . --json` 扫描项目根 + 阶段目录，
    把建议清单念给你听。不会动任何文件。
  ↓
AI：执行命令
  ↓
AI：拿到结果，把 loose_files / suggested_dirs / warnings 翻译成人话：
    - 「发现 18 个散落文件，分类如下：基线 2 个 / 首期 4 个 / 完整规划 9 个 / 客户待确认 3 个」
    - 「建议建 5 个子目录：00-总览 / 01-首期范围 / 02-完整模块规划 / 03-客户待确认 / 04-合规审计」
    - 「警告：future_plan 主题有 9 个散落文件，建议建子目录」
  ↓
AI：停下问人：
    「这套建议方案可以执行吗？
     - A：可以（请告诉我执行哪些——比如全做/只做future_plan）
     - B：调整建议（主题分类不对/某个文件应该分到别处）
     - C：暂不整理」
  ↓
用户选 A/B/C：
  - A：「明白，方案我会由你手动执行（或未来由 --apply 自动执行）」
  - B：AI 调 `delivery layout` 重新扫并细化
  - C：结束
```

## 关键剧本（AI 怎么调）

### Step 1 — 一句话告诉用户要做什么

> 「我现在要调 `delivery layout --root . --json` 扫描项目布局，把建议清单念给你听。不会动任何文件。开始？」

等用户说"开始 / OK / 继续"再调。

### Step 2 — 调 CLI（dry-run only）

```bash
python "${CLAUDE_PLUGIN_ROOT}/delivery.py" layout --root . --json
```

或 `delivery layout --root . --json`（已 `pip install -e .`）

### Step 3 — 翻译 JSON → 人话

输出的关键字段：

| 字段 | 含义 | 怎么念 |
|---|---|---|
| `loose_files` | 散落在根目录的非机器文件 | 「根目录有 N 个散落文件，建议归到 X 个主题子目录」 |
| `loose_files[i].theme` | 文件被归类到哪个主题 | baseline / first_phase / future_plan / pending_customer / compliance / misc |
| `loose_files[i].suggested_dir` | 建议放哪个子目录 | 00-总览 / 01-首期范围 / 02-完整模块规划 / 03-客户待确认 / 04-合规审计 / 99-未分类-待用户裁定 |
| `suggested_dirs` | 建议新建的阶段目录 | 「current_stage 是 X，对应 Y 目录未建，建议建」 |
| `warnings` | 扫描出的注意事项 | 「某主题散落文件过多，建议建子目录」 |

**翻译示例**：

> 「根目录发现 18 个散落文件：
>  - 2 个建议放 `00-总览/`（PRD.md / 客户确认记录）
>  - 4 个建议放 `01-首期范围/`（开发排期 / 制度目录核对 / 后续迭代 / 阶段一Story）
>  - 9 个建议放 `02-完整模块规划/`（完整PRD/SPEC/能力地图/状态机/四层架构/对照表/阶段化/阶段依赖/技术就绪）
>  - 3 个建议放 `03-客户待确认/`
>  - 0 个建议放 `04-合规审计/`
>
> 建议新建 1 个阶段目录：当前阶段 development 对应 `07-开发/` 已存在，下游阶段 eval/qa/acceptance_gate 对应 `08-测试验收/` 已存在。
>
> 警告：future_plan 主题 9 个散落文件，已建议放 02-完整模块规划/。
>
> 这套方案执行吗？」

### Step 4 — 等人点头

**禁止**根据语气词猜测、**禁止**多步合并、**禁止**自动建目录/移文件。

用户回答分支：

- **A. 全做**：「明白，方案已记录。请你手动 mv，或运行 `delivery layout --apply`（未来实现）」
- **B. 只做某主题**：「明白，只做 future_plan。剩余文件保持原位。」
- **C. 调整**：「请说哪个文件归类不对，应放哪里。我重跑扫描。」
- **D. 暂不**：「明白，方案留底。结束。」

### Step 5 — 落回：人手动执行 / 未来 --apply

当前版本**没有 `--apply`**——AI 只出方案，由人手动 `mv`。后续版本会加 `--apply` + 写 `_meta/migration-log.md` 台账。

## 关键纪律（<execution_contract>）

1. **逐步汇报、逐步确认** — 先说要做什么、等用户确认、再调 CLI
2. **不动文件** — 本 skill 永远不动文件，只出方案
4. **不替人拍板** — 多模块判断、主题分类，都先问
5. **产物不动** — 客户签字、关卡结论一律不动
6. **建议必有理由** — 每个 loose_files 项带 `reason`，让人能审计

## 与 delivery-onboarding 的关系

`delivery-onboarding` 在混乱项目接入时也会触发本 skill（4 步法的第 4 步），但 onboarding 偏流程引导；本 skill 偏**单一目的**——只做布局整理。

## 不实现的事

- 不实现 `delivery layout --apply`（当前版本）
- 不实现 dry-run 之外的执行模式
- 不实现文件内容改写（仅移位置，不改内容）
- 不实现跨项目迁移（每个项目独立布局）

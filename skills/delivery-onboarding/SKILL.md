<execution_contract>
本 skill 是「逐步剧本」而非「待办清单」。任何 AI 在执行本 skill 时必须遵守：

1. **逐步汇报、逐步确认**：每个 `<step>` 的 `<action>` 开始前，必须先用一句话告诉用户
   "我现在要做 X，会产出 Y"，等用户明确确认（说"继续"/"OK"/"确认"等）后再执行。
   **禁止**把多个 step 合并执行。**禁止**"先全部做完再统一汇报"。

2. **不确定就停下**：遇到模糊、缺信息、多种合理方案的情况，必须停下来问用户，
   **不得替用户做决定**。

3. **契约交接禁止记忆交接**：每步执行前必须重新读相关源文件/schema/产物，
   不得凭上一步的"印象"直接产出（见 ADR 0009）。

4. **产物默认草稿态**：所有写入正式路径的产物，先写到 `<name>.draft.<ext>`，
   等用户确认后再 mv 到正式路径。

5. **关卡产物不动**：本 skill 产出的关卡结论（客户签字、技术就绪、验收）必须由真人/真合同触发，
   AI 只生成**待签件**和**检测是否已签**，不伪造签字。
</execution_contract>

# 交付流水线入口 / 角色路由（delivery-onboarding）

**目标**：让任何角色（产品经理 / 项目经理 / 研发 / AI 工程师）装上插件后，**不依赖某个人**就能上手：知道自己在流水线哪一环、依据什么干活、下一步调哪个 skill。

**角色**：你是流程引导员。不替用户干活，而是把他领到正确的阶段和工具。

## 分层设计（本模块的定位）

BMAD 在此当方法论脚手架 + 文档工具箱——前端探索、研究、product-brief、PRFAQ、SPEC、引导式 PRD、UX、架构、技术就绪和拆故事能力全开；专人经验换成 coached 引导，新人也能按标准干。**不把** BMAD 的 sprint-status 当执行状态写端：执行状态真源在飞书，本地 `sprint-status.yaml` 只由 `delivery-sprint-sync` 单向刷新；多 agent 重交接、bmb 自举、复盘/圆桌等按需使用，不作为日常主流程强制步骤。

## 全景流水线（谁在哪一环）

```
商机确认→方案/报价→【0:签约】→需求接入→分析立项→PRD→UX+HTML原型→【A:客户签字】→架构/就绪校验→拆任务进飞书→敏捷研发→【B:AI评测】→测试→【C:客户验收】
 售前      售前     售前/商务    PM        PM     PM   PM+UX         项目经理      产品/架构师      项目经理       研发       AI工程师  QA     项目经理
```

方括号 = delivery-flow 自建的**五个关卡**（0 签约 + A 客户签字 + B AI评测 + C 客户验收，加就绪校验技术门）。
**Trace 根 = 商机编号 `OPP-{YYYY}-{NNN}`**：售前在商机确认时生成，签约关卡放行时写入 `project-progress.yaml` 的 `trace_id`，并经立项包播种到 `SPEC.md` 头部引用行——从此商机→SPEC→Story→飞书→评测→验收串成一条可追溯链，商务与交付不再断层。
`SPEC.md`（机读契约）在 PRD 阶段产出，是全链共享脊柱——客户签字范围快照、架构输入、验收依据都从它读机读字段，不靠文件名猜；其 Constraints/Success signal 的上游来源是**立项包**（deal-gate 产出的商务基线），PM 起需求时读立项包，不再人肉转述。

【阶段说明】
0. **售前**（delivery-presales）：商机确认（生成商机编号=Trace 根）→ 委托 BMAD 做商机分析/方案 →（可选）演示原型 → 报价 → 谈判跟进；商机/客户/合同落飞书 CRM（delivery-crm-sync）
0.5 **【0: 签约】**（delivery-deal-gate）：合同签约冻结商务基线，放行产出**立项包**（客户/合同范围/预算工期红线/关键约束），移交 PM 起需求接入。未签约不进需求接入
1. **分析立项**：brainstorming 发散 → market/domain/technical-research 联网深挖 → product-brief / prfaq 锁概念（BMAD 前端探索全开，新人靠 coached 引导问对问题）
2. **规划**：coached PRD（引导式发现）+ bmad-ux（视觉定调）+ **HTML 演示原型**（整页可交互，客户签字前可点着看）+ SPEC.md 机读契约
3. **【A: 客户签字】**（delivery-client-gate）：读 SPEC.md 生成范围快照，客户确认后冻结变更基线
4. **方案化/技术就绪**：四层架构（业务架构 → 产品架构 → 技术架构 → 数据架构）+ bmad-check-implementation-readiness 四文档对齐关卡——PM 拆任务前必须过这道技术门
5. **拆任务推飞书**：epics/stories 拆解（三要素）→ 推飞书三层结构（清单>父任务>子任务）
6. **敏捷研发**：从飞书领活 → Superpowers（TDD/调试/验证）实现自测 → 回飞书改阶段状态
7. **【B: AI 评测】**（delivery-eval-loop）：Tier1 自动化 + Tier2 专家标注
8. **测试**：手动 + bmad-qa-generate-e2e-tests（可选自动化骨架）
9. **【C: 客户验收】**（delivery-acceptance-gate）：对照 SPEC.md + 客户确认记录的 DoD 逐项验收，取得签字

## 项目目录结构规范

### 混乱项目接入（已有项目）

**核心原则：不重命名、不迁移、轻量补建。** 历史项目的「乱」是**现实成本**，重命名带来的回归风险远大于收益。插件架构已为此设计：所有项目级文件（`project-progress.yaml` / `_映射表.json` / `SPEC.md`）都是**可选层**，缺失时 CLI 返回 `status: missing` 而不报错。

**4 步接入**（半小时内可完成）：

1. **创建 `project-progress.yaml`**（参考 `templates/project-progress模板.yaml`）：
   - `current_stage: <推断的当前阶段>`（AI 扫描产物推断）
   - `meta.mode: quick` ← 关键：用快速模式，不要求补全历史
   - `meta.modules: [<实际模块>]` ← 如果是多模块项目

2. **跑 `delivery check --root . --json`**——告诉你哪些产物已存在 / 哪些缺失 / 下一步补什么

3. **跑 `delivery progress --root . --json`**——拿到 `next_action_suggestion`，AI 按此引导

4. **选关键产物补建**（不动人读产物）：
   - 缺失 SPEC.md / PRD.md → 跑 `bmad-spec` 重新生成（不算补历史，是补契约）
   - 缺失客户确认记录 → 走 `delivery-client-gate` 的 B 入口（登记既有确认，不重签）
   - 缺失架构 → 走 `bmad-check-implementation-readiness` 重检

**AI 协助整理脚本**（用户说"整理混乱项目"时触发）：

<action>扫描项目根 + 阶段目录所有文件，按文件名前缀 / 内容关键词推断属于哪个阶段 / 模块</action>
<action>产出「现状快照.md」：**推断的阶段 + 模块归属 + 缺失清单 + 建议补建顺序**</action>
<action>用户确认快照后，**只补建缺失的机器文件**（不动人读产物），写入 `meta.snapshot_at` 标记此次整理时间</action>

每个项目启动时，按以下结构组织文件。**按阶段分文件夹**，文件带顺序编号，文件夹用 emoji 标记当前状态。

### 命名规则

| 元素 | 规则 | 示例 |
|------|------|------|
| 项目根文件夹 | `<项目名>-<年份>` | `学工系统-2026` |
| 阶段文件夹 | `{序号}-{阶段名}` | `01-商机确认`、`06-架构` |
| 人读产物文件 | `[序号] 文件名-日期.md`（仅人读产物带序号） | `[01] 商机档案-2026-08-01.md` |
| 机器文件 | 项目根固定名（无序号） | `SPEC.md`、`project-progress.yaml`、`_映射表.json` |
| 会议记录 | `{日期}-{主题}-{参会人}.md` | `2026-08-03-方案评审会-张总李工.md` |

> **机器文件不带 `[序号] 前缀`**：`SPEC.md` 必须在项目根，命名固定。`core.py` 的 `resolve_artifact()` 兼容带前缀的阶段目录（如 `[04] 04-需求分析/`），但不兼容机器文件名带序号。旧布局 `_meta/` 仅用于兼容存量项目，新项目不推荐。

### 阶段状态标记（文件夹 emoji 前缀）

| 标记 | 含义 | 说明 |
|------|------|------|
| `▶ ` | 当前进行中 | 同一时刻只有一个文件夹带此标记 |
| `✅ ` | 已完成 | 该阶段所有产物已通过关卡 |
| `○ ` | 未开始 | 前置阶段完成后方可进入 |

> **更新时机**：每完成一个阶段并通过关卡后，将 `▶ ` 移到下一个文件夹，上一个自动改为 `✅ `。这个动作本身就是阶段验收的仪式感。

### 文件顺序编号

- 同一文件夹内的文件用 `[01]`、`[02]`、`[03]`... 编号
- 编号表示文件在阶段内的**生成顺序**，也方便引用（如"见 `[02] 报价单`"）
- 编号不跨文件夹连续，每个文件夹从 `[01]` 重新开始

### 客户提供资料管理

- 存放位置：`00-项目资料/客户提供/`
- 原则：**原样存放，不改文件名，不转格式**，保持原始证据链
- 常见内容：需求说明书 PDF、现有系统操作手册、品牌视觉规范、数据样本

### 会议记录管理

- 存放位置：`00-项目资料/会议记录/`
- **两种类型**：
  - **逐字稿**（`-逐字稿` 后缀）：录音转文字的原样记录，作为证据链备查
  - **结构化纪要**（`-纪要` 后缀）：从逐字稿提炼的议题/结论/待办，用于阅读和跟踪
- 命名规则：`{YYYY-MM-DD}-{会议主题}-{参会人}.md`
- 内容：议题、讨论要点、结论、待办（含责任人和截止日期）
- 会议产生的正式产物（如报价单、SPEC）放在对应阶段文件夹，会议记录本身留在 `00-项目资料/`

> ★ `bmad-spec` 的 SPEC.md 是全链机读契约：Why/Capabilities/Constraints/Non-goals/Success signal 五个字段，下游所有关卡（客户签字范围快照、架构输入、验收 DoD）从它读机读字段，不再靠文件名 glob 猜。
> `delivery-prototype-html` 已提供前端原型能力，位于 PRD→客户签字之间，产出整页可交互 HTML 演示（非 bmad-ux 的 2-4 屏静态 mock）。

### 多模块项目（可选）

当项目包含多个独立可交付模块（如电商系统的用户/订单/支付模块，或 ERP 的财务/库存/采购模块），**阶段目录内按模块分子目录**：

**判定标准**（满足任一即应分模块）：
- 客户/P M 在需求里点名了模块名（"用户模块"、"订单模块"）
- 模块可独立交付、独立验收
- 至少有 2 个模块需要独立的 PRD / UX / 架构设计

**规则**：
1. **阶段目录不变**——保留流水线次序（04-需求分析、05-设计、06-架构）
2. **多模块时阶段内分子目录**，模块名由客户/PM 拍板（中文/英文/拼音均可）
3. **模块内文件独立编号**（`[01] PRD.md`、`[02] SPEC.md`）
4. **跨模块产物**（总 PRD、整体架构图、跨模块时序图）放 `00-总览/` 子目录或 `[00]` 前缀
5. **单模块项目不强制子目录**——避免空目录噪音
6. **机器文件无模块归属**：SPEC.md / project-progress.yaml / _映射表.json 仍放项目根

**AI 怎么判断要不要分模块**（Step 0.5 之后）：

<action>**再问用户**（仅交付模式且复杂度 ≥ 中）：

> "这个项目包含多个模块吗？
>
> - **A 单模块**：全部产出放在一个阶段目录里（适合内部工具、简单业务系统）
> - **B 多模块**：每个模块一个子目录（适合电商 / ERP / 跨团队的复杂系统）
>
> 选 A / B？如果 B，请告诉我模块名清单（如：用户、订单、支付）。"

</action>

<action>用户回答后写到 `project-progress.yaml` 的 `meta.modules`（数组），作为后续所有 step 的子目录依据。</action>

### 3 层封顶原则（模块内子模块/子阶段）

**默认不分子模块。** 超过 3 层就要警惕——很可能分错了，应把「子模块」升级为顶层模块。

```
阶段（项目根） →  模块（阶段内）  →  Story 文件（模块内）
   1 层              2 层              3 层 ← 顶
```

**各阶段产物的分层建议**：

| 阶段产物 | 建议 |
|---|---|
| PRD / UX / 架构 | 按**模块**共享，不分子模块 |
| SPEC | 项目根单一文件，跨模块功能写 Capabilities 数组 |
| Story | 按**子功能**分（一个 Story 一个文件），文件名前缀区分 |
| HTML 原型 | 按模块一个子目录（已支持） |

**Story 层分子目录示例**（不分子模块，用文件名前缀区分）：

```
07-开发/stories/订单模块/
├── STORY-001-创建订单.md       ← 子功能：下单
├── STORY-002-支付订单.md
├── STORY-003-取消订单.md
├── STORY-004-查询订单.md       ← 子功能：查询
├── STORY-005-订单详情.md
└── STORY-006-订单退款.md       ← 子功能：售后
```

**什么时候才升级为独立模块**（满足任一）：

- 客户/PM 明确点了子模块名（如「订单管理」+「售后管理」是两个模块）
- 子模块独立交付、独立签字（罕见）
- 子模块跨多团队

否则保持「模块 + Story 层文件命名区分」即可。

## 关卡纪律（团队共识，靠自觉不靠技术锁）

> 诚实说明：这些关卡是**流程约定**，没有技术强制——任何人硬跳过也没程序拦。但跳过=破坏交付可追溯性，团队须共识遵守。

0. **合同没签约 → 不进需求接入**（deal-gate：商务基线未冻结、无立项包，PM 起需求就是无源之水）
1. **客户没签字 → 不进开发**（client-gate）
2. **技术就绪不达标 → 不拆任务**（四层架构 + readiness-check：业务/产品/技术/数据四层 + 四文档对齐是 PM 切任务前的技术门，缺则补回）
3. **任务三要素不全 → 不推飞书**（feishu-sync）
4. **AI 评测 Tier1 不达阈值 → 不进 QA/上线**（eval-loop）
5. **没过客户验收 → 不算交付**（acceptance-gate）
6. 需求真源在文档、状态真源在飞书——回读飞书绝不覆盖文档正文（SSOT）
7. 本地 sprint-status.yaml 是飞书状态的**只读镜像**：通过 `delivery-sprint-sync` 单向从飞书拉取刷新，不反向写飞书

## 两步必须真人（工作流只能检测、不能代替）

- **客户签字**（client-gate 入口 / acceptance-gate 出口）：本质是甲乙双方线下动作，AI 只能生成待签件、检测是否已签。
- **eval Tier2 专家标注**：答案正确率/检索命中率需领域专家给标准答案，专家不到位则挂起，不自造答案。

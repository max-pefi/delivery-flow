# ADR 0009: 上下文与子 agent 边界

- **日期**: 2026-08-07
- **状态**: 已采纳

## 背景

`delivery-flow` 是面向项目交付的 AI 工作流编排插件，AI Agent 会顺着 Skill 链路由售前读到验收。在真实消费方项目上，AI 一次会话可能跑 5-10 个 Skill，期间客户原始资料、SPEC、Story、评测报告、验收记录会被反复加载到上下文。

我们需要回答：

1. 哪些信息必须交给 LLM 之外的东西持有？
2. 什么时候值得派子 agent？
3. 子 agent 与主 agent 之间用什么交接？

## 决策

采纳「**三层架构 + 三条规则**」：

```text
主 agent      —— 只做路由和落盘，不持有原始资料
  ├─ 子 agent —— 压缩输入（读大文件 → 出结构化摘要）
  └─ CLI      —— 校验输出（读文件 → 出退出码）
```

### 规则一：契约交接，禁止记忆交接

每个 Skill 的入口只允许读「固定机器文件 + 本阶段必要产物」，出口必须落盘。跨阶段一律重读文件，不依赖对话记忆。

落点：

- 机器文件清单（`SPEC.md` / `project-progress.yaml` / `sprint-status.yaml` / `_映射表.json` / `_商机映射表.json` / `desired-tasks.json`）固定在项目根，详见 [`产物命名约定.md`](../产物命名约定.md)。
- 每个 Skill 的「step 1」明确列出本阶段必读文件列表，禁止「继续之前对话中讨论的 X」式输入。

这条本质是把插件已有的「机器文件是真源」设计意图（ADR 0001 / 0002）写成硬约束。

### 规则二：子 agent 只用于压缩输入，且只有两个场景

| 场景 | 是否派子 agent | 理由 |
|---|---|---|
| 读 `00-项目资料/客户提供/` 的原始文件 | **派**，一次性子 agent，产出 `[00] 资料摘要.md`（每条结论带原文定位），主线只读摘要 | 唯一真正划算。输入巨大、输出可压缩 10-50 倍，且摘要本身是可留档产物 |
| 生成四层架构（业务/产品/技术/数据） | **可派**，4 个并行子 agent | 输入相同、输出独立、无顺序依赖，是全流程唯一能真正并行的一步 |
| 其他所有阶段 | **不派** | 严格串行，派了只增加交接损耗 |

子 agent 的输出契约固定为结构化摘要：

- 包含 ID / 范围 / 关键决策点 / 原文定位（行号 / 段落 / 页码）；
- 不含 LLM 的主观判断（"这段需求很重要"），只含可机器复核的事实抽取。

### 规则三：放行判断一律走 CLI 退出码，不走 agent 复核

关卡放行前必须跑 `delivery check`，读退出码。子 agent 的产物质量由 `check_project()` 的四态检查负责，不由另一个 agent 的自然语言判断负责。

`delivery-feishu-sync` step 1 已经强制走 `delivery.py check --root . --json` 并读退出码，这是这条规则的落地。

## 被否方案

### A. 派一个总 agent 复核子 agent 产物

不行。理由：

- 总 agent 读了全部上下文，自身就是膨胀源；
- LLM 复核 LLM，结论不稳定，成本高；
- 校验用程序就够了——`delivery check` 是确定性程序，退出码 0/1/2 可信、可测试、零 token。

### B. 在每个 Skill 里都派子 agent 拆任务

不行。理由：

- 大部分 Skill 是串行的（先 A 再 B），派子 agent 只增加交接损耗（主 agent 要把上下文复制给子 agent，再把产物读回来）；
- Skill 的输入通常已经是机器文件（`SPEC.md` 一份 5-20KB），远没到需要压缩的体量；
- 派多了反而干扰调试——失败时不知道是 Skill 错了还是子 agent 错了。

### C. 引入跨会话持久记忆

不行。理由：

- 跨会话记忆会绕过「契约交接」，让 Skill 无法独立运行；
- 与「机器文件是真源」的 SSOT 哲学直接冲突（ADR 0002）；
- 后续插件升级/迁移时不可移植。

## 后果

- 正面：上下文增长可预测，单个会话成本可控；
- 正面：Skill 之间独立可测，不会因为前一个会话残留记忆影响下一个；
- 正面：失败时定位清晰（Skill 错了改 Skill，子 agent 错了改子 agent prompt，CLI 错了改代码）；
- 代价：资料摘取子 agent 的摘要质量决定后续 Skill 的输入质量，摘要不准会传染错误；
- 代价：并行子 agent 产出冲突时仍需主 agent 仲裁，主 agent 要承担合并逻辑。

## 不在范围

- 本轮不实现 `00-项目资料摘取子 agent` 的 prompt 模板（仅规范约束）；
- 本轮不实现 `四层架构并行生成子 agent` 的 prompt 模板（仅规范约束）；
- 不引入 `agents/` 目录、不写 agent 定义文件；
- 不改任何 Skill 的执行流程去调 Task 工具。

下一轮先在真实项目上验证「资料摘取子 agent」一个场景，有效再考虑推广。

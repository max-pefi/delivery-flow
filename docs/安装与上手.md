# 安装与上手 — delivery-flow 插件

> 让新团队从零装好、跑通 delivery-flow，并理解"团队级怎么用"。
>
> **目标读者**：PM / 项目经理 / 流程负责人（非所有成员都需要安装本插件）。
>
> **诚实声明**：delivery-flow 是 Claude Code 工作流规范插件。它依赖三个独立的外部组件，分别属于不同来源，**必须分步安装**。本插件**不包含**飞书 API、评测 runner 或自动门禁执行器——它通过 Skill 文档约定流程，靠团队纪律执行。

---

## 安装全景（按依赖关系分层）

| 层级 | 组件 | 用途 | 安装方式 | 是否必须 |
|------|------|------|---------|---------|
| **L1 插件市场** | `delivery-flow` + `superpowers` | 工作流 + 研发基座 | marketplace.json 注册 + 重启 | delivery-flow 必需；superpowers 推荐 |
| **L2 方法论基座** | BMAD-METHOD v6 | SPEC/PRD/架构/拆故事 | `npx bmad-method install` | 必需 |
| **L3 飞书集成**（可选） | `lark-*` 技能 | 任务推送/状态同步 | 按 lark-* 各自说明 | 仅飞书环节需要 |
| **L4 项目实例** | `project-context.md` + `project-progress.yaml` | 项目级红线与状态 | onboarding 引导生成 | 必需 |

**安装顺序**：L1 → L2 →（L3 可选）→ L4

**重要前提**：delivery-flow 插件未加载时，对话中的 Claude **看不到** `delivery-bootstrap` skill。L1 安装并重启 Claude Code 之前，请按本文档手动执行 L2/L4 步骤。

---

## Part 1 — 安装（分步）

### Step 1 — L1 插件市场注册

在消费方项目根创建 `.claude-plugin/marketplace.json`（如已存在则追加）：

```json
{
  "$schema": "https://anthropic.com/claude-code/marketplace.schema.json",
  "name": "<你的项目>-marketplace",
  "owner": { "name": "你的名字" },
  "plugins": [
    {
      "name": "delivery-flow",
      "source": {
        "source": "github",
        "repo": "fredsimas782-jpg/delivery-flow"
      }
    },
    {
      "name": "superpowers",
      "source": {
        "source": "github",
        "repo": "obra/superpowers"
      }
    }
  ]
}
```

完成后重启 Claude Code（或运行 `claude plugin marketplace update`）让插件生效。

> 若使用本地路径（不连 GitHub），把 `source` 改成 `"./"` 或绝对路径字符串。

### Step 2 — L2 安装 BMAD-METHOD v6

delivery-flow 把 BMAD 当方法论脚手架 + 文档工具箱（产品 Brief / SPEC / PRD / UX / 架构 / Story 拆解），自身**不重复实现**这些能力。

```bash
npx bmad-method install
```

> ⚠️ **验证说明**：此命令形式取自 BMAD 公开文档，**尚未在所有空白项目验证过**。若执行失败，请查阅 BMAD-METHOD 官方仓库获取最新安装方式。安装成功后项目根会生成 `_bmad/` 目录。

### Step 3 — L3 安装飞书技能（可选，仅飞书环节需要）

如果项目需要把任务推到飞书、领活、看状态镜像，必须安装 `lark-*` 技能集：

- 常见依赖：`lark-task`（任务操作）/ `lark-base`（多维表格）/ `lark-shared`（共享工具）
- 安装方式：参考各 lark-* 技能的 `SKILL.md` 或对应插件市场条目
- 凭证：在 Claude Code 中完成飞书 OAuth 授权

> 不做飞书集成可跳过本步。`delivery-feishu-sync` 会因找不到 lark 技能而报错，但不会影响需求接入、PRD、UX、验收等纯文档环节。

### Step 4 — L4 建项目实例文件

在项目根创建 `project-context.md`（**实例层配置文件**，放项目特定约束）：

**方式 A**：跑 BMAD 交互生成
```bash
bmad-generate-project-context
```

**方式 B**：复制模板手动改
从 `templates/project-context模板.md` 复制到项目根，改名为 `project-context.md`，填入项目名、预算红线、技术栈、性能验收线、AI 评测阈值等。

> `project-context.md` 是 AI Agent 的"宪法级"注入文件——预算、技术红线、性能验收线、风险防线全部写在这里，消费方项目必须存在。

`project-progress.yaml` 可以等插件加载后由 `delivery-bootstrap` 自动生成。

### Step 5 — 触发 onboarding，开始引导

L1 插件加载完成后，在 Claude Code 对话中说 **"我该做什么"** 或 **"装 delivery-flow"**，会触发 `delivery-onboarding` 或 `delivery-bootstrap` skill。

Onboarding 会自动检测：
- L1 基座是否就位（delivery-flow + superpowers）
- L2 BMAD 是否安装
- L4 `project-context.md` 是否存在
- 识别你的角色（产品经理 / 项目经理 / 研发 / AI 工程师）
- 定位当前在流水线哪个阶段
- 路由到对应 skill

## Part 2 — 谁驱动 + 如何引导角色

### 核心原则

> **onboarding 是引导入口，通常由 PM / 流程负责人驱动**，不是每个团队成员各自开 Claude Code 跑一次。一人用 onboarding 驱动 → 产出飞书任务 / 客户确认件 → 通过飞书/文档分发 → 团队从飞书领活。

### 角色 → 工作依据 → 主责阶段 → 调用

| 角色 | 工作依据 | 主责阶段 | 调用的 skill / 工具 |
|---|---|---|---|
| **售前 / 商务** | 客户咨询/线索 + 客户诉求原文 | 商机确认 → 方案/报价 → 签约 → 立项移交 | `delivery-presales`（生成商机编号=Trace 根、委托 BMAD 分析）、`delivery-deal-gate`（签约冻结商务基线、产立项包）、`delivery-crm-sync`（商机/客户/合同落飞书多维表格） |
| **产品经理** | 立项包 + `project-context.md`(红线) + `SPEC.md`(机读契约) | 分析立项 → PRD → UX+HTML原型 | BMAD brainstorming / research / product-brief / prfaq / spec / prd / ux、`delivery-prototype-html` |
| **UX / 原型负责人** | SPEC + PRD + `project-context.md` | 视觉与交互设计 → HTML 演示原型 | `bmad-ux`、`delivery-prototype-html` |
| **项目经理** | SPEC.md + 已签字客户确认记录 | 客户签字 → 方案化就绪 → 拆任务推飞书 → 验收 | `delivery-client-gate`、`bmad-architecture`、`bmad-check-implementation-readiness`、`bmad-create-epics-and-stories`、`delivery-feishu-sync`、`delivery-acceptance-gate` |
| **架构师 / 技术 Lead** | SPEC.md + PRD | 方案化/技术就绪 | 四层架构模板（业务/产品/技术/数据）、`bmad-check-implementation-readiness` |
| **研发工程师** | 飞书子任务 + story AC + `project-context.md`(验收阈值) | 敏捷研发 | 从飞书领活 → Superpowers（TDD/调试/验证）→ 自测 → 回飞书改阶段状态 → `delivery-sprint-sync`（单向刷新本地状态镜像） |
| **AI 工程师** | stories/AC + 阈值 | AI 评测 | `delivery-eval-loop` |
| **QA** | Story AC + SPEC Success signal + 评测报告 | 测试与回归 | 人工测试、`bmad-qa-generate-e2e-tests` |
| **流程维护者** | 项目产物 + 本地状态镜像 | 一致性检查、追溯、预演 | `delivery-check`、`delivery-trace`、`delivery-status`、`delivery-dry-run` |

> `delivery-sprint-sync` 只从飞书单向刷新本地状态镜像，不是第二个状态写端。

### 现实模式：一人驱动，全员跟飞书

```
PM/项目经理 驱动 onboarding
    ↓
产出客户确认记录 / 飞书任务
    ↓
通过飞书/文档分发给团队
    ↓
研发从飞书领活 → 改状态 → PM 跟飞书看进度
```

- 团队其他人**不需要**装 Claude Code，也不需要触发 onboarding。
- 他们从飞书领任务、改阶段状态即可参与。
- 项目经理通过飞书看板一眼看全局。

## Part 3 — 完整走一遍（示例流程）

以下展示一个典型 AI 应用项目从需求接入到验收的全流程，每步标注调用的 skill 和产出物。

```
Step 0   售前：商机确认（生成商机编号=Trace 根）+ 方案/报价
          ↓  delivery-presales / BMAD research
          ↓  产出：商机档案-{日期}.md + 报价单-{日期}.md + 演示原型/

Step 0.5 【0: 签约关卡】deal-gate
          ↓  delivery-deal-gate
          ↓  产出：合同签约确认记录-{日期}.md + 立项包.md（冻结商务基线）

Step 1   需求接入与分析立项
          ↓  BMAD brainstorming / research / product-brief / prfaq
          ↓  产出：产品 Brief / PRFAQ

Step 2   产品规划
          ↓  bmad-spec / bmad-prd / bmad-ux
          ↓  产出：SPEC.md + PRD + DESIGN.md / EXPERIENCE.md + 线框

Step 3   HTML 交互原型（售前演示已做则跳过，正式原型可选）
          ↓  delivery-prototype-html
          ↓  产出：可离线运行、可导航、可点击的 prototype/

Step 4   【A: 客户签字关卡】client-gate
          ↓  delivery-client-gate
          ↓  产出：客户确认记录-{日期}.md（A 新签 / B 存量登记 / C 变更确认）

Step 5   方案化/技术就绪（四层架构 + readiness）
          ↓  bmad-architecture / bmad-check-implementation-readiness
          ↓  产出：业务架构/产品架构/技术架构/数据架构 + readiness-report.md

Step 6   拆任务推飞书
          ↓  bmad-create-epics-and-stories + delivery-feishu-sync
          ↓  产出：飞书「清单 > 父任务 > 子任务」+ _映射表.json

Step 7   研发实现（从飞书领活）
          ↓  Superpowers（TDD/调试/验证）
          ↓  研发在飞书改「阶段状态」= 开发中 → 测试中 → 已上线
          ↓  delivery-sprint-sync 单向刷新本地 sprint-status.yaml 镜像

Step 8   【B: AI 评测关卡】eval-loop
          ↓  delivery-eval-loop
          ↓  产出：评测集.md + 评测报告.md（含门禁结论）

Step 9   测试 / QA
          ↓  人工测试或 bmad-qa-generate-e2e-tests

Step 10  【C: 客户验收关卡】acceptance-gate
          ↓  delivery-acceptance-gate
          ↓  产出：验收报告-{日期}.md（对冻结范围核 KPI/DoD，取客户签字）

完成交付（project-progress.yaml 置 current_stage: null）
```

> **硬顺序**：客户签字后，必须先通过四层架构与技术就绪检查，才能拆任务推飞书。

### 关键纪律

1. **合同未签 → 不进需求接入**（deal-gate：商务基线未冻结、无立项包，PM 起需求就是无源之水）
2. **客户没签字 → 不进开发**（client-gate）
3. **技术就绪不达标 → 不拆任务**（四层架构 + readiness-check：业务/产品/技术/数据四层 + 四文档对齐是 PM 切任务前的技术门，缺则补回）
4. **任务三要素不全 → 不推飞书**（feishu-sync）
5. **AI 评测 Tier1 不达阈值 → 不进 QA/上线**（eval-loop）
6. **没过客户验收 → 不算交付**（acceptance-gate）
7. 需求真源在文档、状态真源在飞书；本地 `sprint-status.yaml` 只是飞书的只读镜像

> 以上关卡是团队共识的流程约定，没有技术强制。但跳过 = 破坏交付可追溯性。
